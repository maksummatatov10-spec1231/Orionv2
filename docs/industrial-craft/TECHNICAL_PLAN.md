# Industrial Craft for Orion — технический план

## 1. Исходная точка

Сейчас готова **текстурная** сборка v0.5: заменяются пиксели внутри существующих изображений, код игры не меняется. Проверка подтверждает 274 целевых региона и неизменность остальных тегов. Это хорошая художественная база, но само по себе оно не добавляет рецепты, станки или электричество.

Отдельно проверен запуск добавленного ActionScript-кода в тестовой копии SWF: тестовый `VerifyBootstrap` получает `Context`, работает с инвентарём, блоками и стенами. Это доказывает возможность внедрения кода, но ещё не доказывает готовую архитектуру мода, сохранение новых сущностей или работу нового интерфейса.

**Вывод:** следующий шаг — технический прототип, а не массовая отрисовка станков.

## 2. Что найдено в коде Orion

Источники ниже — декомпилированные справочные файлы в `analysis/as3/`. Они не являются готовым проектом, который можно без проверки скомпилировать целиком.

| Область | Наблюдение | Следствие для IC |
|---|---|---|
| Предметы | `Item.ITEMS` — фиксированный `Vector.<Item>(4096, true)` | Нужен реестр свободных числовых ID и стабильные имена `ic:*`; ID нельзя менять между версиями |
| Блоки | `Block.BLOCKS` — фиксированный `Vector.<Block>(256, true)` | Блоков значительно меньше, чем предметов; сначала проверяем остаток свободных мест |
| Иконки | Конструктор `Item` ищет `item_<id>` и `item_light_<id>` в атласе `items` | Для новых предметов нужен не только рисунок, но и регион атласа с метаданными |
| Рецепты | Есть `Recipe`, категории и списки, включая `MACHINERY`; `Crafting` проверяет/списывает ингредиенты | Можно опереться на существующую модель рецептов, проверив доступность категории в интерфейсе |
| Станки | `TileEntity` имеет `update`, `save`, `load`, `remove`; печь уже хранит слоты, топливо и прогресс | Берём печь как образец жизненного цикла, но не копируем её ошибки/жёсткие рецепты |
| Фабрика сущностей | `TileEntity.createTileEntity` — switch по известным типам; заголовок пишет тип/x/y через `writeShort` | Новая сущность требует интеграции фабрики и формата либо отдельного версионированного слоя данных |
| Мир | Размер по умолчанию 600×500, клетка 32 px; логика tile-сущностей накапливает 1000 мс | Энергетический тик проектируем под реальный ритм Orion; не обещаем 20 тиков/с |
| Регионы | Есть `regionEnter`/`regionExit`, но `updateTilesEntites` обходит все сущности с `needUpdate` | Поведение удалённых от камеры фабрик задаём явно и проверяем |
| Сохранение | `GameSaver` вызывает сохранение мира; есть полный и частичный пути; локально используются `SharedObject` `world`/`player` | Нужны обе проверки: обычное сохранение и автосохранение/частичный путь |
| Локализация | `Text.init` читает JSON; `Item.setName` требует существующий ключ | Новые RU/EN ключи добавляем до создания предметов |
| Взаимодействие | `DefaultItemsInteract` открывает панели печи, сундука, верстака; `Controller.setItemsInteract` публичный | Ищем минимальную точку подключения своих интерфейсов без переписывания всего контроллера |
| Генерация руд | `OresGenerator` создаёт залежи по глубине при генерации мира | Новые руды подключаем к генерации и отдельно решаем миграцию старых миров |
| Энергия | `EnergyBeamTileEntity` — игровой луч/коллайдер, а не готовая сеть электричества | Не используем одно название как доказательство наличия EU-сети; сеть пишем отдельно |
| Батарея | `Item.BATTERY` уже существует как предмет | Не путаем компонент крафта с новым аккумулятором, хранящим заряд и подключаемым к сети |

## 3. Предлагаемая архитектура

Рабочее пространство имён — `industrialcraft`. Игровой код отделён от ресурсов и сборочных скриптов.

```text
IndustrialCraftBootstrap
  ├─ ContentRegistry     предметы, блоки, ключи локализации, ID
  ├─ RecipeRegistry      рецепты и производственные таблицы
  ├─ MachineManager      состояния, жизненный цикл, тики станков
  ├─ EnergyNetwork       граф кабелей, источники, потребители, буферы
  ├─ Persistence         версия формата, сохранение/загрузка/миграция
  ├─ Interaction/UI      правый клик, панели, подсказки, измеритель
  ├─ WorldIntegration    генерация руды и одноразовая миграция мира
  └─ AssetPipeline       атласы, новые регионы, частицы, звук
```

### Важное решение этапа 0

Сравниваем два способа внедрения:

1. **Минимальные точечные изменения существующего ABC и добавленный код мода.** Нужны для фабрики сущностей, жизненного цикла, интерфейса или сохранения, если публичной точки подключения нет.
2. **Добавленный центральный менеджер плюс существующие публичные точки/сигналы.** Меньше вмешательства в оригинальные классы, но состояние станков может потребовать отдельного слоя сохранения.

Не выбираем способ только по красивому прототипу. Критерий — надёжное сохранение, удаление, загрузка и совместимость с базовой игрой.

Добавление ABC-тега само по себе не заменяет существующие методы. Тестовый загрузчик подтвердил запуск нового класса, но для производственного мода нужен проверяемый список точек внедрения.

### Данные вместо жёсткой логики

Предметы, рецепты и параметры станков описываются таблицами со стабильными ключами:

```text
ic:copper_ore
ic:copper_dust
ic:rubber
ic:insulated_copper_cable
ic:fuel_generator
ic:macerator
```

Числовой ID назначается один раз, проверяется на конфликт и сохраняется в манифесте. Таблицы рецептов содержат входы, выходы, время, энергию и требуемую категорию. Баланс меняется без переписывания обработчиков интерфейса.

## 4. Реестры, атласы и ID

Этап 0 обязан сделать инвентаризацию занятых ID в реальной сборке, а не доверять только текстовому поиску по декомпиляции.

Требования:

- не переполнить фиксированные векторы предметов/блоков;
- не занять ID существующего предмета, блока или служебного состояния;
- проверить диапазоны и преобразования ID при сохранении;
- выделить диапазоны IC и зафиксировать их в манифесте;
- для каждого нового предмета добавить имя, описание, иконку, регион атласа и запись в проверочном списке;
- для каждого нового блока проверить тайл, предмет в руке, инвентарь, дроп и разрушение;
- не менять ID после выпуска сохранения без миграции.

Нынешний сборщик v0.5 заменяет существующие прямоугольники и проверяет, что пиксели вне них не изменились. Добавление новых регионов атласа — отдельная задача: может потребоваться расширить изображение и обновить XML-метаданные. Это нельзя выдавать за уже готовую возможность texture-only сборщика.

## 5. Сохранения — главный технический риск

Минимальный формат состояния IC должен содержать:

```text
formatVersion
worldIdentity / saveSlotFingerprint
contentIdManifestVersion
machines:
  stableId, type, x, y
  slots, energy, progress, activeRecipe, upgrades
networkTopologyVersion или восстановимые соединения
worldGenerationFlags
```

Точный формат выбирается после проверки двух путей:

- расширение существующих `TileEntity` и их сериализации;
- отдельный версионированный блок данных IC, связанный с миром и устойчивыми ID.

Обязательные проверки:

1. Полное сохранение → закрытие игры → загрузка.
2. Частичное/автоматическое сохранение во время работы станка.
3. Сохранение при неполном прогрессе и отсутствии энергии.
4. Перемещение/демонтаж станка без дублирования содержимого.
5. Загрузка мира, где часть фабрики далеко от игрока.
6. Отсутствие данных IC у старого мира: чистая миграция без повреждения базового сохранения.
7. Более новая версия данных в старой сборке: понятный отказ, а не тихая порча.
8. Ошибка записи/квоты локального хранилища: видимое сообщение, а не ложное «сохранено».

`SharedObject` для отдельного мода не считаем автоматически надёжным: проверяем `flush`, повторную загрузку, привязку к правильному миру и ограничение размера. Сначала поддерживаем локальный одиночный путь; онлайн-сохранения остаются отдельной задачей.

## 6. Сборка и совместимость

Базовый SWF хранится вне Git по существующей практике. Не добавляем ещё одну 60-мегабайтную копию оригинала ради каждого этапа.

Будущая структура:

```text
modding/industrial-craft/
  src/                 ActionScript мода
  data/                предметы, блоки, рецепты, параметры, локализация
  assets/              исходники новых спрайтов и интерфейса
  scripts/             сборка, проверка ID, атласов, ABC и SWF
  verification/        отчёты и контрольные игровые скриншоты
  build/               генерируемые SWF, не коммитятся
```

Сборка должна выдавать манифест:

- SHA-256 исходного и результирующего SWF;
- версия IC и версия формата сохранений;
- список изменённых/добавленных тегов;
- список точек внедрения в оригинальный код;
- назначенные ID и регионы атласов;
- результаты автоматических и runtime-проверок.

Текстурный v0.5 остаётся отдельной проверяемой базой. Геймплейная сборка не должна случайно потерять принятые текстуры. AIR-заглушки и тестовая выдача предметов не попадают в релизный SWF.

## 7. Первый спринт: этап 0

### Задачи

- [ ] Поднять отдельный каталог геймплейного мода и воспроизводимую dev-сборку.
- [ ] Сделать аудит свободных ID блоков/предметов и проверить ограничения сохранения.
- [ ] Выбрать способ внедрения кода на маленьком примере.
- [ ] Добавить один тестовый предмет `ic:probe` с собственной иконкой и RU-названием.
- [ ] Добавить один тестовый блок: установка, разрушение, дроп.
- [ ] Добавить один тестовый рецепт через существующую систему крафта.
- [ ] Открыть простейшую панель по взаимодействию с блоком.
- [ ] Выполнить несколько тиков операции и изменить состояние счётчика/слота.
- [ ] Сохранить и загрузить состояние без потери и дублирования.
- [ ] Проверить удаление блока и очистку подписок/таймеров.
- [ ] Сделать скриншоты мира, инвентаря, рецепта и панели до/после перезапуска.
- [ ] Записать выбранные точки внедрения, ограничения и оценку следующего этапа.

`ic:probe` — только технический предмет. Он не входит в релизный контент и не заменяет будущие материалы.

### Критерий выхода из этапа 0

Одна сборка проходит весь маленький цикл без тестовой выдачи как костыля производственной логики. Состояние действительно переживает перезапуск. Понятно, сколько свободных ID осталось и какие изменения оригинального ABC необходимы.

Если сохранение или внедрение кода не работает, этап 0 не закрывается красивыми скриншотами статичного блока.

## 8. Постоянная проверка качества

### Логика

- Рецепты: корректные входы/выходы, отсутствие отрицательных количеств.
- Энергия: сохранение энергии, лимиты буфера, разрыв/цикл/разветвление сети.
- Станки: нет сырья, нет энергии, полный выход, демонтаж, удаление.
- Инвентарь: переполнение, дроп, повторное удаление, заряд предметов.
- Сохранения: полный/частичный путь, версии, миграция, отказ записи.

### Игра

- Новый мир и уже существующий мир.
- Обычное выживание без тестовой выдачи.
- Перезапуск Flash и повторная загрузка.
- Большая сеть: ориентир для нагрузочного теста — 100 станков и 1000 кабелей; фиксируем реальное время тика и отзывчивость, а не обещаем FPS заранее.
- Скриншоты каждого нового интерфейса и состояния, лог ошибок, сравнение с предыдущей сборкой.

## 9. Риски и запасные решения

| Риск | Что делаем |
|---|---|
| Мало свободных ID блоков | Сначала аудит; объединяем состояния через данные сущности там, где это безопасно; не увеличиваем вектор вслепую |
| Нельзя надёжно расширить `TileEntity` | Централизованный менеджер плюс версионированный слой данных; проверяем все пути сохранения |
| Добавленный ABC не перехватывает нужный метод | Минимальный точечный патч с манифестом и проверкой неизменного остального кода |
| Новые регионы атласа ломают загрузку | Отдельный маленький тест атласа до добавления десятков иконок |
| Большие сети тормозят игру | Перестройка графа по изменениям, активные тики только там, где есть работа; нагрузочный тест |
| Старые сохранения теряют новые предметы | Стабильные ID, версии формата, резервная копия перед миграцией, явный отказ при несовместимости |
| Объём расползается | первый релиз ограничен двумя станками; реактор, мультиплеер и точная копия IC2 не входят в MVP |

## 10. Ближайшее действие

Начинаем с этапа 0. По его результату фиксируем архитектуру и только затем делаем медь/резину и первую энергосеть. Так мы не потратим этап на красивые станки, которые нельзя сохранить или подключить к игре.
